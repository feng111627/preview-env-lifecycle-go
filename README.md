# preview-env-lifecycle-go

按需预览环境的生命周期管理。用本地内存资源（`LocalProvisioner`）模拟命名空间与配额，
保证多人同时开环境、到期回收、失败重试时占用状态一致且失败原因可区分。
在共享复用与全局容量管控下，空闲环境可被后来的申请直接复用，
全局活跃环境总数受统一上限约束，账面上的占用与真实底层资源始终一致。

## 生命周期状态

```
                Create / Acquire（池空时新建）
                  │
            provisioning ──Provision 失败──▶ failed（占用回滚，从占用表摘除）
                  │ Provision 成功
                  ▼
                ready ──Bind──▶ in_use
                  │  ▲            │ （InUse 不被回收、不可被复用；Touch/Bind 会续期）
                  │  │Release     │Release（仅所有者，且未被他人绑定）
                  ▼  │            ▼
              共享池（pooled, ready）
                  │  ▲
   原主 Bind 拿回  │  │Release（拿回后可再次释放，可反复进出池）
   （清 pooled、   │  │
    占用记回本人）  │  │
                  └──┴──────Acquire（他人复用）──▶ in_use（Sanitize 清理后交付新使用者）
                  │ 到期且无人使用（含池内空闲）
                  ▼
                reaped（Reap 回收，占用释放）
```

- `Create` 幂等：同名环境已活跃时直接返回已有环境，并发提交不会产生两份。
- 创建先在占用表占位再调底层资源；失败时仅回滚自己写入的占位，同名可立即重建。
- `Destroy` 先释放占用再销毁底层资源，避免重建竞态造成泄漏或重复占用。

## 共享复用与全局容量

- **全局容量**：`Quota.MaxGlobalEnvs` 限制全局活跃环境总数（provisioning/ready/in_use，
  含共享池内的）。到顶后新建申请返回 `ErrCapacityExhausted`，
  可用 `errors.Is` 判定，与 `ErrQuotaExceeded`（个人额度）、`ErrPermissionDenied`（权限）
  三类拒绝互不冒充。
- **共享池**：所有者用 `Release(name, requester)` 把空闲环境释放进池。
  池内环境不计入任何个人配额，但仍计入全局容量；到期照样被 `Reap` 回收。
  仅所有者可释放（越权返回 `ErrPermissionDenied`）；重复释放是幂等 no-op。
  进池后的出路只有三种：原主 `Bind` 直接拿回、他人 `Acquire` 复用、到期 `Reap` 回收，
  每一种都会把状态收敛到唯一一致的结果，不会悬在中间态。
- **复用**：`Acquire(ctx, user)` 优先从池中取一个空闲环境，
  经 `Provisioner.Sanitize` 就地清理（不增删底层资源）后交付，占用从原主让出、记到新使用者头上，
  环境总数不虚增；池空时才新建（受全局容量约束）。复用本身不增加全局计数，
  因此全局到顶时复用仍然可行。
- **原主直接拿回（不走申请）**：空闲环境进池后，原主可以用 `Bind(name, owner)` 直接拿回自用，
  无需重新走一遍 `Acquire`。拿回按“正常投入使用”处理：
  - 清除池内空闲标记（`Pooled=false`），占用重新记到原主名下（`Owner/BoundTo=原主`、`in_use`），
    之后表现与正常申请到的环境完全一致：受使用中保护（不被回收/复用/腾挪）、可续期、可再次释放、可销毁。
  - 拿回要过个人配额判定（池内期间不计个人占用）；个人额度用满返回 `ErrQuotaExceeded`。
    拿回不新增全局环境，因此不会返回 `ErrCapacityExhausted`。
  - 非原主不能用 `Bind` 绕过复用流程拿走池内环境，返回 `ErrPermissionDenied`；
    他人复用池内环境必须走 `Acquire`（含 Sanitize 清理与占用交接）。
  - 整个判定在同一把锁内原子完成，没有锁外步骤，因此“拿回”要么成功（占用正确入账、池标记清除），
    要么在改动任何状态之前被明确拒绝（环境仍在池中、可被正常复用），不存在半成品。
- **账实一致（不允许幽灵占用）**：任何时刻，全局活跃数都满足
  `ActiveCount == 池内空闲数 + 已被认领的活跃数 == 底层真实资源数`。
  池内空闲环境（`Pooled=true`）一定是 `ready` 且未绑定任何人；活跃且非池内的环境一定有唯一认领人。
  因此不会出现“既没人认领、又回收不掉、又不能被复用，却占着全局名额”的中间状态：
  池内空闲的到期会被 `Reap` 回收、会被 `Acquire` 复用；被拿回后则像正常使用中一样参与后续生命周期。
  并发下同一环境只会被一方拿到（原主拿回与他人 `Acquire` 争抢同一池内环境时，先到者得，
  其余得到明确的容量/配额/权限拒绝），不会分给两人，也不会分出超过真实可用的数量。
- **交接失败补偿**：`Acquire` 复用在锁外执行 `Sanitize` 清理。清理失败时认领被撤销：
  占用不计到申请用户头上、环境恢复为原主名下的池内空闲状态（`Pooled=true/ready/unbound`），
  环境不丢不重，错误返回 `ErrReuseFailed`——与容量不足（`ErrCapacityExhausted`）、
  个人额度用满（`ErrQuotaExceeded`）、没有权限（`ErrPermissionDenied`）四类原因互不冒充。
  补偿后原主仍可直接拿回，或清除故障后再次被他人复用。
- **保护**：正在使用（InUse）或刚被重新激活（续期）的环境不会被复用、腾挪或回收。
  原主拿回会重新续期，因此池内到期瞬间被拿回的环境不会被紧接着的 `Reap` 回收；
  同批未被拿回的池内到期环境仍照常回收。
- **并发**：认领、拿回、释放、回收都在同一把锁下判定，并发抢池不超发、
  同一环境不会分给两人。
  `ActiveCount()` 可与底层实际资源数（如 `NamespaceCount()`）对账。

## 配额与权限规则

- 配额：`Quota.MaxEnvsPerUser` 限制单用户活跃环境数（provisioning/ready/in_use 均计入，
  池内环境除外）。超限拒绝，错误可用 `errors.Is(err, ErrQuotaExceeded)` 判定。
- 权限：仅所有者可 `Destroy`/`Release`；环境只能被所有者领取（`Bind`），已绑定环境他人不可抢。
  越权拒绝，错误可用 `errors.Is(err, ErrPermissionDenied)` 判定。
- 三类拒绝原因（全局容量/个人配额/权限）互不混淆。
- 回收：`Reap` 只回收**到期且非 in_use** 的环境（含池内空闲环境）；`Bind`/`Touch`/`Acquire`
  会续期（重新激活），刚被激活的环境不会被误回收；重复 `Reap` 是幂等 no-op。

## 本地验证

```bash
go build ./...      # 编译
go test ./... -v    # 单测，日志打印关键输入与判定依据
go test -race ./... # 并发竞态检测
```

测试覆盖：并发同名创建去重、并发异名创建计数一致、创建失败回滚与重建、
配额/权限/全局容量三类拒绝原因区分、到期回收与使用中保护、重复回收幂等、回收后重建无泄漏、
空闲环境释放与复用（占用转移、清理验证、计数不虚增）、全局到顶时复用仍可行、
并发抢池不超发不重复分发、复用清理失败的补偿与重试、
**进池后原主直接拿回（池标记清除、占用记回本主、与正常申请表现一致）、
拿回的配额/权限拒绝区分与拒绝后仍可复用、池内到期后拿回与回收交叉、
拿回→再进池→他人复用→销毁的账实一致、拿回与 Acquire 并发争抢不重复分发不超发、
经历拿回循环后复用失败的补偿、含拿回路径的混合并发（申请/拿回/释放/销毁/回收交叉）账实对账**。

所有单测日志带 `[business=...]` 标签，可看出覆盖的业务场景、每条用例的输入与判定结果；
`ledgerSane` 辅助断言在关键用例中校验
`ActiveCount == 池内空闲数 + 已认领活跃数 == 底层命名空间数`，并检查无幽灵占用。
